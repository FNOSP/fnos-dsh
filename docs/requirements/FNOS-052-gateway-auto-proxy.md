## 需求背景

应用经飞牛统一网关开放，入口固定在 `/app/fn-deepseek-harness`。DSH 内的插件如果按**站点根绝对路径**暴露接口（例如 `/dsh-market/...`、`/dsh-taskboard/...`），浏览器发出的请求落在网关前缀之外，飞牛网关不会把它转发给应用，页面拿到的是宿主的 404。

现有解法是让用户自己去发现这件事：打开浏览器调试面板，从失败请求的 URL 反推前缀边界，再到 `dsh-fnos` 详情页的「三方插件 proxy」逐行填写，保存后刷新。这条路径有三个问题：

- **发现成本高**：用户要先意识到「某个功能坏了」是路径前缀问题，再会看调试面板，还得判断前缀该截到哪一段。
- **猜错没有反馈**：填错前缀不报错，只表现为功能依旧不可用，用户容易在「填了没用」和「不知道该填什么」之间循环。
- **装插件就要维护配置**：每装一个用绝对路径的三方插件都得重复一次，而这份知识本来就在应用里——插件是在本进程注册的路由。

本需求把这个发现动作交给应用自己完成：**插件注册了什么前缀，应用就知道；应用知道就自动接进网关，用户什么都不用填。**

## 调研结论

| 结论 | 出处 | 影响的功能 |
| --- | --- | --- |
| 飞牛统一网关只把 `gatewayPrefix` 下的请求转发给应用，且该前缀必须形如 `/app/{appname}[/...]`，没有通配能力；HTTP 与 WebSocket 路由都应保持在该前缀下 | [fnnas-docs 统一网关](https://developer.fnnas.com/docs/core-concepts/gateway-registration)（`references/core-concepts/gateway-registration.md`） | FNOS-052-01、02 |
| 本应用入口只注册了 `/app/fn-deepseek-harness`，因此前缀之外的请求**根本到不了应用进程**，网关侧无法做兜底转发 | `apps/fn-deepseek-harness/app/ui/config` | FNOS-052-01、02 |
| 浏览器侧的路径改写通道已经存在：网关在页面注入 bridge，按「内置前缀 + 用户配置前缀」把同源绝对路径改写到应用前缀；配置前缀经 SSE 实时下发，新增前缀无需刷新页面 | `packages/fnos-gateway/src/client/bridge.ts`、`src/server/path-allowlist.ts`、`src/server/gateway-server.ts` | FNOS-052-02、03 |
| 因此自动适配不需要新增网关能力，缺的只是「哪些前缀属于本应用」这份知识 | 上两条合成 | FNOS-052-01 |
| DSH 宿主 web 服务在 0.2.2-rc.1 **没有**路由枚举 API，也**没有**注册事件；公开接缝只有 `register`、`registerUpgrade`、`registerFallback`、`tapIndex`、`readResource`，事件只有 `webserver/index-inject` | `@deepseek-ai/dsh-host-webserver@0.2.2-rc.1` 的 `lib/types/index.d.ts` | FNOS-052-01、05 |
| 路由表以 `exact` / `prefixes` 两张表保存在服务实例上，`register()` 是唯一写入入口，返回的 disposer 负责撤销 | 同上 `lib/index.js` 的 `register` 与 `match` | FNOS-052-01、04 |
| 真实插件的注册形态确实是「一级路径段」：`dshmarket` 注册 51 条 `exact` 路由，全部位于 `/dsh-market/*`；`dsh-taskboard` 注册 `prefix: /dsh-taskboard` 与 `exact: /dsh-taskboard/events` | 已安装 profile 的 `node_modules` 实读（2026-11-09） | FNOS-052-01 |
| 宿主未命中路由的响应是可判别的：GET 返空 body 的 `404`（无 `content-type`），非 GET/HEAD 返 `405` 且 `allow: GET, HEAD`；已注册保存型路由对不支持的方法返回自己的 allow 列表 | 本地实测（DSH 0.2.2-rc.1、2026-11-09，`curl` 直连宿主端口） | FNOS-052-03（仅作为降级方案的可行性依据） |
| 但上述判别**无法覆盖 SSE 与 WebSocket**——这两类连接不能「先失败再重试」，首次连不上就没有第二次机会 | 同上实测 + 浏览器 API 语义 | FNOS-052-02 |
| 飞牛宿主自身占用 `/static`、`/cgi`、`/app` 等命名空间，文档明确插件不应读取宿主的静态目录布局 | fnnas-docs 统一网关与入口文档 | FNOS-052-04 |

结论：**方案可行，但技术上必须依赖 DSH 宿主服务的运行时路由表**（无公开枚举接缝），因此实现要把「读不到」当作正常分支处理，而不是异常。

## 需求目标

| 编号 | 功能 | 用户可观察结果 |
| --- | --- | --- |
| FNOS-052-01 | 自动识别路由前缀 | 安装使用绝对路径的三方插件后，其接口自动可用，用户无需填写任何前缀 |
| FNOS-052-02 | 浏览器侧自动接入 | 被识别的绝对路径请求（普通请求、事件流、WebSocket、图片与样式资源）自动经应用网关转发，无需刷新页面 |
| FNOS-052-03 | 手动配置降级为可选 | 自动识别生效时，「三方插件 proxy」不再是必填步骤；自动识别不可用的环境仍可手动填写并照常工作 |
| FNOS-052-04 | 接管边界与生命周期 | 宿主保留的命名空间与网关内置前缀永不被接管；插件停用或卸载后其前缀自动撤销 |
| FNOS-052-05 | 状态可见与降级说明 | 插件详情页展示当前自动生效的前缀与识别状态；无法识别时说明原因，而不是静默失效 |

### FNOS-052-01 自动识别路由前缀

应用在自身进程内获知「有哪些插件注册了哪些路由」，按一级路径段归并成前缀集合。识别同时覆盖两种来源：应用启动前就已注册的路由，以及启动后新注册的路由（用户装插件不必重启应用）。

识别只看路径的首个路径段：`/plugin-api/get/me` 归并为 `/plugin-api`，`/dsh-market/api/v1/capabilities` 归并为 `/dsh-market`。这与现有手动填写口径一致——用户在提示里看到的例子就是「API 是 `/plugin-api/get/me`，就填 `/plugin-api`」。

### FNOS-052-02 浏览器侧自动接入

被识别的前缀进入网关下发的前缀集合后，浏览器页面即可把同源绝对路径改写到应用前缀下。由于网关已按「前缀变更即推送」的方式工作，新前缀**不需要刷新页面**生效，也不需要用户重新打开应用。

这一条必须覆盖事件流与 WebSocket：任务看板一类插件把事件流挂在 `/dsh-taskboard/events`，它没有「失败重试」的机会，只能靠请求发出前就知道该走哪条路。

### FNOS-052-03 手动配置降级为可选

「三方插件 proxy」输入框保留，但语义从「必填清单」变为「补充清单」：

- 自动识别生效时，用户可以完全不填；
- 自动识别覆盖不到的情况（插件借用了非本进程注册的路径），手填仍然有效；
- 手动项与自动项同时存在时并存生效，手动项不因自动识别而被覆盖或清空；
- 用户可以关掉自动识别，让行为完全回到当前版本（纯手动），用于排查。

### FNOS-052-04 接管边界与生命周期

- **宿主保留命名空间永不接管**：飞牛宿主自己使用的路径（如 `/static`、`/cgi`、`/app`）以及网关内置前缀（`/api`、`/plugins`、`/__fnos-gateway` 等），即便插件真的注册了同名前缀，也不进入自动集合。
- **文件形态路径不接管**：首个路径段本身像文件名的（含 `.` 的段），不按前缀接管。
- **随插件生命周期回收**：插件停用或卸载时，它注册的路由被撤销，其前缀也应随之从生效集合中消失，不留残影。
- **自动区段只读**：用户不能编辑自动识别出的条目，只能整体开关自动识别；要改就改手动区段。

### FNOS-052-05 状态可见与降级说明

详情页在「三方插件 proxy」区域展示：

- 当前自动接管的前缀（只读列表，与现有「系统内置」只读区同一呈现口径）；
- 自动识别的状态：已启用 / 已关闭 / 当前环境不可用（附原因）。

自动识别不可用时，界面必须明确说出来并引导用户手填，而不是让配置区看起来「一片空白但依然不工作」。

## 行为约束

- 现有手动填写的前缀、已落盘的数据与既有用户配置全部保留，升级后不回退、不丢失。
- 旧版本网关读取新格式配置时，行为必须等价于「只读手动区段」，不能因为多了字段而整份拒绝。
- 网关对浏览器页面的改写规则（内置前缀、CSS/HTML/JS 资源改写）保持不变。
- 不修改 DSH 上游代码；对宿主路由信息的读取只发生在插件进程内。
- 应用对外暴露的入口仍只有 `/app/fn-deepseek-harness`，不新增任何外露路由。
- 自动识别不影响未使用绝对路径的插件：这类插件此前能用，升级后仍然能用。

## 不在本次范围内

- **未被 DSH Web 路由承载的绝对路径**：插件把请求打到宿主或外部服务、自身不注册路由的，应用无从得知，仍需手动填写。这是本方案的固有边界。
- **推动 DSH 上游提供路由枚举 API**：作为长期建议记录，不在本需求实施。
- **fnOS 宿主页面自身的路径改写**：宿主页面的绝对路径不属于本应用职责。
- **多用户隔离与权限模型调整**：沿用[FNOS-017](/requirements/FNOS-017-fnos-route-403) 既有的同源判定口径。
- **为自动识别新增面向外部的查询接口**：状态只在应用自己的插件详情页内呈现。
