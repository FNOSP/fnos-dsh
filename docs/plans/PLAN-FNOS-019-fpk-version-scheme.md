## 目标与范围

把项目/FPK 版本从「语义化档位递增」改为「固定前缀 + 迭代号递增」，并让 DSH 基线由 catalog 自动承载。插件版本流程保持原样。

## 关键设计决定

### 版本拆解不能用「按 `-` 切一刀」

版本串 `5.9.0-0.2.1-rc.2.5` 里出现两个 `-`：第一个分隔基础版本与尾部，第二个属于基线自身的预发布段（`rc.2`）。因此基线边界只能从**尾部**定位：末尾的 `.` 之后是迭代号，其余为基线。

### 一处固有歧义及其消解方式

`5.9.0-0.2.1-rc.2` 既可读作「基线 `0.2.1-rc.2`、缺迭代号」，也可读作「基线 `0.2.1-rc`、迭代号 `2`」——**两者产生完全相同的字符串**，仅凭版本串无法区分。

消解方式：拆解函数接受可选的「已知基线」参数。提供时按基线前缀唯一匹配——尾部恰好等于基线即视为缺迭代号（迭代号 0），否则按 `<基线>.<数字>` 取迭代号。计算下次版本时**必须**传入基线，否则缺迭代号的版本会被误读成迭代号 2，导致下次跳号到 3。

### 基线变化时迭代号重置为 0

基线变化（DSH 升级）时迭代号从 0 重新开始：`5.9.0-0.2.1-rc.2.5 → 5.9.0-0.2.1-rc.5.0`。迭代号只在同一基线内才有比较意义——基线变了，先后由基线本身决定（`…-0.2.1-rc.5.0` 必然大于 `…-0.2.1-rc.2.5`），所以重置不会造成排序倒退。真正会倒退的是同一基线内把迭代号改小，那种情况必须继续 +1。

### 基础段用正则校验形态，不写代码常量

「`5.9.0` 静态不动」的落法有两种：把它写成代码常量并在不符时报错，或只校验形态、值由版本号自身承载。**选后者**：常量会让「调整基础段」必须改代码，且常量与实际版本号可能悄悄不一致；校验形态则让版本文件成为唯一事实来源，代码不认识那个字面量。

同样的判断适用于串内基线：它可能与 catalog 当前基线不同（DSH 刚升级、版本文件还是旧基线）。这是**合法过渡态**——若把它判成非法，基线升级那次发布会解析不出当前版本，迭代号被迫归零，正好撞上本方案要避免的排序倒退。

### 显式版本交给 bumpp，不用语义化档位

`bumpp` 的 `release` 选项接受具体版本串。因此自行算出目标版本后以显式值传入，仍由 `bumpp` 负责文件替换、release 提交与本地 tag——不引入新的版本工具，也不改提交与 tag 行为。

档位关键字（`patch`/`minor`/`major`）保留参数形态，语义统一收敛为「迭代号 +1」；传入完整版本串时按其字面值写入。

## 风险与决策

| 项目 | 风险或决策 | 处理方式 |
| --- | --- | --- |
| 预发布排序 | `5.9.0-*` 按 semver 小于 `5.9.0`，已装正式 `5.9.0` 的设备可能拒装新版本 | 列为必测项（AC-05）；实测确认平台行为后再定处置，不默认可用 |
| 平台比较实现未知 | fnOS 应用中心如何比较版本未从文档确认 | 只做实测，不假设；两版各打一个 FPK 在设备上验证 |
| 尾部歧义 | `…rc.2` 既可读作缺迭代号也可读作迭代号 2 | 拆解时传入已知基线消歧，并在单测中固定该行为 |
| 基线来源 | 手工维护基线副本会与 catalog 漂移 | 一律从 `pnpm-workspace.yaml` 读取，缺失时报错 |
| 基础段常量 | 把 `5.9.0` 写成常量会让调整基础段必须改代码，且常量可能与版本文件不一致 | 代码只校验形态，基础段从当前版本串原样继承 |
| 迭代号上限 | 迭代号为单段整数，无上限设计 | 当前无实际约束；若未来溢出可按需扩展，不在本次范围 |
