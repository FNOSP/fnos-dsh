## 计划目标

把「其它 403」变成可切换的账号级失败：独立错误码 → 进入换号集合 → 可见提示。内容拦截与 401 的既有语义保持不变。

## 当前实现与目标设计

| 领域 | 当前实现 | 目标实现 | 迁移影响 |
| --- | --- | --- | --- |
| 403 分类 | `401 || 403` 统一映射 `AUTH` | 先判内容拦截（11128）与受限（11140 + `request illegal`），其余 403 归 `ACCOUNT_FORBIDDEN`；401 仍为 `AUTH` | 非受限 403 的错误码由 `AUTH` 变为 `ACCOUNT_FORBIDDEN` |
| 换号触发 | 额度 / 限流 / 受限 | 追加 `ACCOUNT_FORBIDDEN` | 403 触发切换 |
| 自动切换偏好 | 拦住额度/限流；受限例外 | `ACCOUNT_FORBIDDEN` 同样例外（账号已被上游拒绝，保持原账号只会继续失败） | 偏好语义不变，例外集合扩大为「账号级失败」 |
| 切换提示 | 按原因分三类 | 追加「账号被上游拒绝（HTTP 403）」 | 提示更准确 |
| 受限集合 | 仅 11140 写入 | **不写入**：403 可能是临时策略拒绝，长期排除会误伤 | 403 只在本次请求内排除（已尝试集合） |

### 为什么 403 要例外于自动切换偏好

与 FNOS-023 同一理由：该账号已被上游拒绝，继续用它只会重复失败；切换是恢复可用性的唯一手段，而可见提示保证用户知情。

### 为什么不把 403 记入受限集合

11140 是**持续**的账号状态（需重新登录），因此跨请求排除是合理的；其它 403 可能只是某次请求的策略拒绝（例如内容/来源判定），把它当作长期状态会让一个可用账号被永久跳过。因此只在**本次请求**内排除（复用既有的「已尝试」集合）。

## 依赖、风险和决策

| 项 | 说明 |
| --- | --- |
| 依赖 | 无新增依赖 |
| 风险一 | 若上游用 403 表示「请求内容问题」，换号仍会失败并多消耗一次尝试。缓解：单次请求内尝试次数由账号数封顶（既有约束），失败如实抛出 |
| 风险二 | 误把内容拦截当 403 换号：已有业务码前置判定兜住（11128 先于 403 分支） |
| 决策 | 403 不写入受限集合 | 与 11140 的持续性不同，避免把可用账号长期跳过 |
| 决策 | 403 与受限一样绕过自动切换偏好 | 账号已被拒绝，保持原样只会继续失败；以可见提示交换用户知情 |
